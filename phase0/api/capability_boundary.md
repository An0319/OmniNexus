## 零、已修复缺陷的残留约束（调用方仍必须遵守）

| # | 缺陷与修复 | 调用方必须做什么 |
|---|---|---|
| B1 | 时间线**源全挂退出 0** 已修复（`99c84eb`）：`events.json` 顶层 `status` 取 `ok / partial / failed`，全部源失败时退出码为 `3`，`--replay` 恒为 `ok`。但 **`partial` 时退出码仍是 0，且结果只覆盖成功的源**。 | **任何调用方都必须看 `status`，不能只看退出码与 `events` 数量**：`ok` → `events` 为空才是真"没有事件"；`partial` → 标注"只覆盖部分源"；`failed` → 不得当作结果。仍建议逐源核对 `sources_stats` 的 `error` 与 `fetched`。 |

## 一、事件时间线（timeline）

| # | 可以依赖什么 | 不能依赖什么 |
|---|---|---|
| 1 | 可以依赖：每条入表事件都同时具备来源 URL、抓取时刻、原文片段三样，缺一即被拒绝入表。 | 不能依赖：入表 = 事件真实发生过；入表只说明"有来源这么写了，且抽得出结构化字段"。 |
| 2 | 可以依赖：`events.json` 是"带来源的候选表"，可用于人工复核、日报线索、下钻入口。 | 不能依赖：把它当结论或当事实库直接展示给终端用户。 |
| 3 | 可以依赖：`event_id` 稳定可复现（同输入同 id），可做主键与去重键。 | 不能依赖：同一事件一定只有一个 id；跨源不同措辞的事件会各留一条。 |
| 4 | 可以依赖：质量按输入条件分两行——只有标题：召回 0.875 / 精确 0.778（可计 8 条）；标题 + 正文首段：召回 0.833 / 精确 0.833（可计 12 条）；均为 n=23、主口径。 | 不能依赖：这些数字能外推到"任意主题、任意时间窗"；样本只有 23 条，只有标题轮 23/23 条无摘要，补正文轮只补了 6 条且标注存在污染。 |
| 5 | 可以依赖：判不了占比可分开报——只有标题 26.1%（6/23）；标题 + 正文首段 4.3%（1/23）。 | 不能依赖：**没有**"判不了"的条目等于"没发生"；它们只是抽不出动作或主体。 |
| 6 | 可以依赖：`rejects[]` 会逐条给出拒绝原因（8 种规则态 + 2 种模型态），可用于展示"哪些被丢掉、为什么"。 | 不能依赖：`duplicate` 会进 `rejects`；合并项只计入 `merged_duplicates`，内容已在表内、URL 仍在 `sources[]`。 |
| 7 | 可以依赖：`status`（`ok / partial / failed`）能区分"全部源成功 / 部分失败 / 全部失败"；`sources_stats` 再给出逐源明细。 | 不能依赖：进程退出码 0 等于一切正常——**`partial` 时退出码仍是 0，结果只覆盖成功的源**（见 §零-B1），必须读 `status`。 |
| 8 | 可以依赖：`--replay` 离线复跑与联网跑计数逐项一致，可做可复算回放。 | 不能依赖：直接调 `timeline.run()` 拿返回值取数据；它只返回退出码，数据在文件里。 |
| 9 | 可以依赖：`action` 在可判定条目上准确率 0.857（只有标题 6/7）、0.700（标题 + 正文首段 7/10），够做粗分类与筛选。 | 不能依赖：`action` 精确到业务语义；机构类标题的 `launch` 会被判成 `trial_start`，两轮都如此。 |
| 10 | 可以依赖：`subject` 准确率 1.000（只有标题 7/7）、0.900（标题 + 正文首段 9/10），可做主体聚合。 | 不能依赖：`subject` 一定是具名主体；"类别"（如 `Private equity`）会被当主体误入表，两轮都如此。 |
| 11 | 可以依赖：`value.number` 会给出数值片段，可作为线索提示。 | 不能依赖：`value.number` 与该动作正确绑定；规则路线取"最早出现的数值"。 |
| 12 | 可以依赖：对不存在的主题会返回**空但结构完整**的结果（`status=ok`），不会抛异常。 | 不能依赖：空结果能被区分成"无数据"还是"查询词打错"；两者结构完全相同。 |
| 13 | 可以依赖：抓取失败不会中断整轮，其它源照常出结果。 | 不能依赖：失败一定会体现在退出码；`partial` 时退出码是 0，必须按 §零-B1 读 `status` 与逐源 `error`。 |
| 14 | 可以依赖：成本为 0 元（全部公开源，无 key、无边车）。 | 不能依赖：延迟可控；同一命令本次实测 18.3 s，冷启动首轮更慢，耗时由源站响应决定。 |

## 二、事件注册闭环（registry）

| # | 可以依赖什么 | 不能依赖什么 |
|---|---|---|
| 15 | 可以依赖：判据不合规（含糊、缺字段、源取不到、时间线矛盾）在注册那一刻被拒，账本零新增。 | 不能依赖：注册成功等于判据与那句话意思一致；**语义错配机器查不出**（说"上涨"而判据写 `lte` 也照收）。 |
| 16 | 可以依赖：`criterion_sha256` 可校验判据未被事后改动，账本哈希链可只读校验。 | 不能依赖：哈希链能证明"某条判定在预注册的判据下成立"之外的东西；它证明的是账本未被改写。 |
| 17 | 可以依赖：`hit` / `miss` 一旦落账即冻结，重跑被拒，无法"刷到命中"。 | 不能依赖：判定能被无限次挑战；除 `undetermined` 外不接受重判。 |
| 18 | 可以依赖：`undetermined` 有明确原因码（无数据 / 不可达 / 判不了），可分组展示。 | 不能依赖：`status` 字段能区分三种失败态；三种都写成同一个 `undetermined`，必须读 `reason_code`。 |
| 19 | 可以依赖：`reconcile` 的命中率只对 `hit+miss` 计分母，`undetermined` 与"尚无判定"单列。 | 不能依赖：命中率有统计意义；n < 20 时源码自己只报 Wilson 区间并明说"不足以给点估计"。 |
| 20 | 可以依赖：`not_due` 与 `frozen` 被显式标注，不会混进判定结果。 | 不能依赖：`counts` 里只有三种状态；`not_due` / `frozen` 也占位置，解析时不能按固定三种写死。 |
| 21 | 可以依赖：判据支持 FRED 与 Yahoo 两类源，聚合覆盖 `min/max/last/mean/pct_change`、比较符限 `gte/lte`。 | 不能依赖：支持任意数据源；新增源要在 `sources.py` 的 `PROVIDERS` 登记并实现解析，不是加个字符串。 |
| 22 | 可以依赖：注册时会真实探一次数据源（含行数、首末日、sha256），"当下取不到"会立刻拒。 | 不能依赖："注册时取到"等于"核验时新鲜"；月度序列天然滞后，只能靠 `WINDOW_NOT_COVERED` 兜底。 |
| 23 | 可以依赖：每次核验耗时实测 2–4 s（含进程启动与 pandas 导入）。 | 不能依赖：单次取数短；`TIMEOUT=90 s` 且**无重试**，源半死时批量核验会长时间卡住。 |
| 24 | 可以依赖：账本 append-only，单条追加，写入时刻由调用方显式传入，脚本不读系统时钟。 | 不能依赖：账本时刻已归一 UTC；传入带时区偏移的串会**原样落账**（实测 `+09:00` 可通过）。 |
| 25 | 可以依赖：`chain-check` 只读，可在展示前做一次完整性自检。 | 不能依赖：`undetermined` 只能补跑一次；代码对 `undetermined` 允许**多次**补跑（实测两条记录）。 |
| 26 | 可以依赖：`chain-check` 能验证账本原始文本未被改动。 | 不能依赖：账本被"读进来再写回去"（哪怕内容等价）后仍通过校验——哈希锁原始行文本，重排即 `ok=false`。 |
| 27 | 可以依赖：判定结果落账带 `observed`（窗口、n、首末观测日、聚合值）与来源指纹，可外部复核。 | 不能依赖：结果能复现成"同一条序列同一天再跑一次"；上游序列修订会变，指纹只保证"当时拿到的是这份"。 |

## 三、据此可做的产品决定 / 不可做的产品决定

| 可以据此做 | 不可以据此做 |
|---|---|
| 做"事件线索面板"：列表 + 来源 + 抓取时刻 + 拒绝原因抽屉。 | 做"事件事实确认"：任何形如"已确认发生"的措辞。 |
| 做"注册 → 到期 → 结论"的判定工作台，展示 `hit/miss/undetermined` 与原因码。 | 做"预测命中率排行榜"或对外宣称准确率；n 小、无显著性检验。 |
| 把 0 元 / 2–4 s / 1.2–1.8 s 当作容量与成本基线。 | 把耗时按"每条固定毫秒"做 SLA 承诺；抓取占大头且波动一个量级。 |
| 用 `--replay` 做离线回放与可复算演示。 | 用回放结果作为"线上实时能力"的证据。 |
| 把失败态分三类、各给一句人话。 | 把三类失败态合并成一句"暂无数据"，或把 `undetermined` 折算成未命中。 |
| 展示"判不了：只有标题 26.1% / 标题 + 正文首段 4.3% + 会漏机构声明 + 类别会被当主体"。 | 展示"效果良好 / 准确率约九成"这类无口径、无分母的说法。 |

## 四、必须先补什么，才能解锁更强依赖

| 想解锁的能力 | 必须先解决什么 |
|---|---|
| 更高的可判定率（把"只有标题"下的 26.1% 压下来） | 输入要带正文首段：本窗口 23/23 条只有标题；小样本补 6 条正文后判不了从 6/23 降到 1/23，但要产品化得先解决"每条都带正文首段"的抓取覆盖与入库口径。 |
| 壳能安全地"一条命令拿结果" | 补库级薄包装（现有 `run()` 只返回退出码）；`status` 已落在 `events.json`（`99c84eb`），薄包装只需把它一起返回（见 api.md §5-①）。 |
| 界面能区分三类失败态而不靠壳自己维护映射 | 在判定输出里加 `reason_class` 字段（见 api.md §5-②）。 |
| 判据与那句话的语义一致 | 人工复核 + 展示 `claim_canonical`（判据归一化后的可读句）给用户确认；机器无法自证。 |
| 支持 FRED / Yahoo 之外的数据源 | 按三步 SOP 接源：探针 → 口径卡 → fetcher + 登记 `PROVIDERS`。 |
